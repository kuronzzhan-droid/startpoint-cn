# Wiki 管理员队伍码接口

服务端兼容两种队伍码：现有本地 10 位码继续从服务端数据库读取，12 位码从 Wiki 管理员接口读取。两者都使用游戏原有的 `/party/refer` 请求和原生 `battle_party` 响应。

## 服务端配置

在运行服务的私有 `.env` 中增加一项：

```dotenv
COMMUNITY_TEAM_CODES_URL=https://wf-mod-wiki.pages.dev/api/community/game-codes
```

该值是只读 API 的基址，服务端实际请求 `GET {基址}/{队伍码}`。公网地址必须使用 HTTPS；本地测试可以使用回环地址的 HTTP。不要把实际 `.env`、管理员密码或其他 Wiki 凭据提交到 Git。

当前游戏入口对应的完整路径为：

- CN 服务：`/api/index.php/party/refer`
- 全局服务：`/latest/api/index.php/party/refer`

这是服务端到 Wiki 的请求，不需要浏览器 CORS，也不需要把 Wiki 管理员会话传给游戏服务。

## Wiki 返回格式

对每个码返回 `application/json`，正文必须严格包含以下字段，大小不超过 16 KiB：

```json
{
  "title": "管理员推荐阵容",
  "active": true,
  "team": {
    "main": ["c…", "c…", "c…"],
    "unison": ["c…", "", ""],
    "weapon": ["w…", "", ""],
    "soul": ["w…", "", ""]
  }
}
```

每个数组必须有 3 个槽位。主角色槽不能留空，其他槽位用空字符串表示。角色 ID 必须是 `c` 加 12 位小写十六进制字符，武器和能力魂槽必须是 `w` 加 12 位小写十六进制字符。角色不能重复，Wiki 不应发送原始数值 ID。

公共 ID 的计算规则必须与服务端一致：

```text
c/w + SHA-256("wf-wiki-public-v1:" + kind + ":" + raw_id).hex().slice(0, 12)
```

`kind` 为角色时使用 `c`，武器时使用 `w`。能力魂槽也填写其来源武器的 `w...` 公共 ID，服务端再依据本地资源表映射为能力魂 ID。Wiki 不需要保存或传入玩家培养数据。

## 管理员操作语义

- 创建：Wiki 管理员生成 12 位码，写入上述阵容和 `active: true`。
- 撤销：将 `active` 改为 `false`，或让接口返回 404/410。
- 修改：更新同一个码的 JSON；服务端成功结果缓存最多 5 秒。
- 玩家读取：服务端根据玩家当前拥有的角色、武器、能力魂和角色培养数据生成预览。缺少资源的槽位留空，读取不会扣库存或写玩家存档。

本服角色表（基础表加 rank_p5b 覆盖表）或装备表里没有的队员、武器、能力魂 ID 按未拥有处理，该槽位留空；只有队长 ID 本服不存在时整码不兼容。

如果玩家没有管理员阵容指定的主角色（队长），该码对该玩家不兼容，服务端返回 `3403`，不会返回可保存的空队长阵容。其他未拥有槽位仍按上述规则留空。

服务端错误映射如下：

| Wiki 响应 | 游戏结果码 |
| --- | ---: |
| 200 且格式有效 | 1 |
| 404/410、码不存在或已撤销 | 3404 |
| 超时、网络错误、非 JSON、格式不兼容，或队长角色 ID 本服不存在 | 3403 |

服务端会限制 IP、viewer 和 player 的请求频率，并把上游错误归一化，不把 Wiki URL、响应正文或凭据写入游戏响应。

## 上线顺序

1. Wiki 先提供一个正式管理员创建的真实码，并确认 200 JSON、撤销后的 404/410 和 HTTPS 证书正常。
2. 用当前客户端确认输入框能接受 12 位码；附件中的旧 SWF 静态检查不能替代这一步。
3. 在目标服务的私有 `.env` 增加 `COMMUNITY_TEAM_CODES_URL`，重启已有服务实例。
4. 使用真实码验证预览、缺少资源留空、确认保存和撤销失效；再确认玩家存档没有新增或扣减。

服务端没有向 Wiki 回写码的接口，管理员创建、修改和撤销都由 Wiki 管理端负责。
