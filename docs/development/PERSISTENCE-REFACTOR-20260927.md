# 服务端运行时与持久化重构

## 目标

为 HTTP、实时多人 TCP、主数据库、辅助 worker 和定时任务建立明确的运行边界。所有主数据库写入最终通过统一的持久化入口完成；实时房间和 TCP 处理不得同步等待数据库提交。

## 当前基线

- 主服务仍由一个 CN Node 进程承载 HTTP、房间状态和 TCP 会话。
- 主数据库使用 `better-sqlite3`，启用 WAL；同一数据库仍只有一个写入者。
- 响应编码、NPC 队伍池、种子持久化、存档导出和管理清理已经使用独立 worker 或只读连接，迁移时保留其现有数据所有权。
- 多人房间已经有进程内 `EmbeddedMultiCoordinator`，因此房间状态不应被拆成逐战斗帧 RPC。
- 代码库仍有若干领域直接调用 `db.transaction()`；这些调用属于后续迁移清单，不能通过只迁移共斗来宣称完成。

## 2026-10-02 四核 CPU 优化补充

本节记录本轮与持久化边界直接相关的最终状态。完整动作、基准、测试和部署参数见 [四核服务器 CPU 优化实施记录](MULTICORE-CPU-OPTIMIZATION-20261002.md)。

- 主连接和 persistence worker 启动时都保留 `wal_autocheckpoint=1000`，不会因为“计划启动外部 worker”而提前放弃安全 owner。
- checkpoint worker 首次成功后才通知主连接和 persistence worker 切换为 `wal_autocheckpoint=0`。
- checkpoint worker 连续三次执行异常或退出后，两个业务连接恢复 `wal_autocheckpoint=1000`；后续 checkpoint 成功可以重新接管。
- checkpoint worker 关闭时先等待 `closed` 或线程退出，最长 5 秒后才强制 terminate。
- persistence worker 不再固定使用 `synchronous=NORMAL`，而是继承统一的 `FULL/NORMAL`、`cache_size` 和 `mmap_size` 配置，并向诊断层报告实际 PRAGMA。
- `runPersistenceTransaction` 新增 `afterCommit`。数据库 COMMIT 成功后才执行 seed/movie 等非持久副作用；该回调失败只记录错误，不把已提交事务伪装成失败重试。
- 抽卡的扣费、奖励、历史、积分、任务、Awake、Degree Mission 和响应组装已收进同一玩家事务；资金、票券和 campaign 也在玩家队列内重新读取。
- 当前 persistence worker 仍只覆盖已命令化的少量写入，不能据此启动多个完整 CN 业务进程。

专项测试覆盖 PRAGMA 继承、1000/0 所有权切换、事务回滚、checkpoint backlog、固定读事务、维护写锁竞争与分阶段回收、启动失败恢复、连续异常降级、重新接管和优雅关闭。

## 本次高负载优化

- TCP 每个连接每次事件循环最多处理有限数量的完整帧，剩余帧通过 `setImmediate` 继续处理，避免单个连接的消息突发延迟其他房间的心跳和广播；同一连接内的帧顺序保持不变。
- 领取历史维护将删除事务默认批次从 1000 行降为 250 行，并支持 `RECEIVE_HISTORY_RETENTION_DELETE_BATCH_ROWS` 调整；批次间即使暂停为 0 也会经过 `setImmediate` 让出事件循环。
- RAID_EVENT 成功结算直接使用原子账本更新返回的 Boss 和关卡计数，避免在同一结算事务前重复读取一次全局状态和关卡统计。

这些调整降低主事件循环的突发占用，但没有把 TCP 变成独立进程，也没有改变奖励、结算或数据库事务边界。独立 TCP/房间进程仍属于后续架构阶段。

## 本批第一步

- 新增 `persistence-coordinator`，为主数据库事务提供业务域、玩家串行队列和统一耗时指标。
- 共斗奖励事务、共斗事实事务、单人结算、邮件领取、任务结算、账号登录/绑定/引继、管理清理和设备注册先接入该入口，保持原有事务边界和同玩家串行语义。
- TCP 大厅的 `ChangeParty` 只先更新房间内存态并广播，partySlot 保存改为低优先级异步持久化；五重决战 continue 也增加异步 HTTP 入口，保留同步兼容函数给旧测试和内部调用方。多人房间人数上限仍为三人。
- Node 24 worker 诊断增加每个 worker 的累计 CPU 时间和采样窗口增量，同时记录主进程同一时间窗的 CPU 增量，用于验证多核心是否实际被使用。
- 仍需保留同步 API 的旧调用方通过兼容入口接入；这些调用不会伪装成异步 worker，后续需要命令化后才能真正搬离主事件循环。
- SQLite checkpoint worker（`SQLITE_CHECKPOINT_WORKER`）在 4 核多核模式默认开启，可显式设为 `0` 关闭。在线定时、启动及手动请求的 checkpoint 均只使用 `PASSIVE`，默认间隔 5 秒。旧 `SQLITE_CHECKPOINT_TRUNCATE_FRAMES`、`SQLITE_CHECKPOINT_TRUNCATE_BYTES` 和 `SQLITE_CHECKPOINT_TRUNCATE_COOLDOWN_MS` 不再启用在线截断；`FULL`、`RESTART`、`TRUNCATE` checkpoint 须放到停止业务写入并排空后的维护窗口。
- 普通可写连接初始化及重开使用 `journal_size_limit=-1`。后台 checkpoint worker 仅完成重 PASSIVE 回写；完整回写且 WAL 大于 2 GiB 时，父进程把最终回收加入持久化写入 gate 的同步排他回调。既有异步写任务排空后，在同一主线程调用栈中由独立维护连接执行最终 PASSIVE，再以 `BEGIN IMMEDIATE`、原值 `user_version` 小提交触发自然重置。普通主线程 Sync/raw SQL 无法插入这段调用栈，也不新增持有 exclusive 跨 await 的拒绝窗口。默认主线程每窗最多释放 256 MiB，紧接 COMMIT 前按真实长度选择 `max(2 GiB, size-256 MiB)`；helper 的全局 1 GiB 上限保留。低于目标不新开维护连接或额外写入。已有维护请求排队时合并重复请求，一次同步回调只缩一次，不在同一回调内连续追赶。
- 独立主线程维护连接使用 `synchronous=FULL`、`busy_timeout=0`、`wal_autocheckpoint=0`，业务连接设置不变。SQLite 层的维护 BEGIN 忙仍正常让位，不作为 checkpoint_error；其他错误回滚后上报。写线程从初始化到有效 ready/settings，或从实际派发到最终 SQL ACK/真实 exit，均持有 native 写入票据；调用者 timeout/rejectAll 不等于原生连接已停写。维护在 native writer 未结束时保持待执行，不持排他 gate 等 IPC。排行榜仍使用原有排他 gate 持有到真实 exit 的规则。
- 长 reader 可能使 PASSIVE 只完成部分回写，此时跳过物理回收，释放后后续轮次继续。2 GiB 是安全重置后的保留目标，不是活跃 WAL 的硬上限；应结合逻辑帧、已回写帧和物理字节诊断。维护线程停用或退出时，业务写入及原有 autocheckpoint 所有权机制继续运行，但物理空间回收暂停，恢复维护后继续分段。启动、手动请求及定时轮次遵循同一规则，不另加主动截断或自动恢复路径。
- `[MEM]` 保留兼容的截断计数、后台 PASSIVE 帧数和物理 WAL 字节；另记录父进程实际回收窗口、尝试、最终 PASSIVE 或 BEGIN 忙、观察到的重置、净减少字节以及 last/max 回收窗口耗时。`reclaimErrors` 同时计入总 errors，后台 checkpoint 所有权仍由后台 PASSIVE 成败决定。WAL 代际在持 WRITE 后与 COMMIT 后比较，重置观察不等于物理净减少。最终尾部回写和缩文件会占主线程、推迟 HTTP/IPC 回调及释放 gate 的请求完成；字节上限不是 I/O 时限，须结合实际窗口、整条请求和 TCP/loop 样本验收，不能以 errors=0 宣称无影响。
- 持久化协调器在连续异步事务之间通过 `setImmediate` 让出一次事件循环，保持同一全局/玩家队列的顺序，同时避免大量结算写入以微任务链形式连续占用 TCP/HTTP 回调。
- 五重多人 `/abort` 和五重单人 `/start` 的 HTTP 路径已改用异步持久化协调器；原有同步函数仍保留给旧测试及已处于外层事务的内部调用，避免放弃或入场请求在主事件循环中直接执行完整 SQLite 事务。
- 公告列表、公告详情和强制公告的已读回执也改用异步持久化入口；同步函数只保留给公告投放查询和管理清理等兼容调用，避免普通客户端浏览公告时直接执行 SQLite 写入。
- 关注关系的新增、删除、移除粉丝和批量编辑接口也改用异步持久化入口；保留同步兼容函数给内部事务调用，关注状态、上限校验和响应字段保持原样。
- 新增可选的业务 SQLite persistence worker 命令通道，使用独立连接、串行命令队列、事务回滚、忙锁重试和关闭 drain；默认关闭。当前先迁移多人大厅低优先级的 party slot 保存和公告回执作为可回退样本，未命令化的复杂业务事务仍使用主进程协调器。
- 战斗事实中的队伍种族统计、队长 Power Flip 统计也经过 `mission` 持久化入口；嘉年华历史迁移和奖励领取表初始化按数据库连接缓存已完成状态，避免每次页面读取或结算重复排队维护事务。
- 深渊最佳时间版本刷新在任务读取发现旧记录时才执行更新，并统一标记为 `single-quest` 写入；无过期记录的普通读取仍保持只读路径。
- 主服务关闭时会等待异步持久化队列 drain，再停止 checkpoint worker，避免低优先级大厅写入撞上数据库关闭。

本轮继续扩展了入口覆盖范围：五重决战（内部 `five-boss` 流程）的单人/多人 start、finish/abort、单人转多人清理、LevelNext/Finalize 证明记录、登录加载维护、排行榜定时结算、每日邮件定时派发、Raid/Rush 活动接口，以及普通单人战斗启动、角色突破/批量突破、羁绊领取、角色来源领取、星之碎片兑换、箱式抽卡执行、装备强化/批量强化/保护设置、关卡解锁、体力恢复、体力道具、EX 强化、装备分解、剧情结算、新手教程奖励、个人资料、玩家历史、支付到账、队伍组编辑、嘉年华默认队伍补全和管理面板玩家清理入口，都已标注业务域并经过持久化协调器。排行榜到期停榜仍同步完成，发奖和计划推进排入队列；活动、普通业务接口和管理面板继续保持原协议响应。

本阶段审计又补齐了容易被旧协议路径绕过的账号边界：旧版 `/tool/signup` 的默认存档与 viewer 会话创建、新版设备注册的账号/设备绑定/旧会话轮换/新会话插入、过期会话清理，以及管理面板的存档改名、存档克隆、账号备注、继承密码重置、设备备注和公告回执清理，都现在通过 `account` 或 `admin` 持久化命令完成。克隆和新设备注册的本地管理状态只在数据库事务提交后更新；重复设备注册会先在同一事务内删除旧 viewer 会话，再插入复用的 token，避免留下半完成会话。

幂等阶段先落地支付完成回调：当客户端提供 receipt 或 transaction_id 时，服务端按玩家和商品建立持久化回执，在同一 `player` 事务内检查回执、增加货币并记录结果。网络重试或进程重启后再次提交同一回执只返回原结果，不会再次增加虚拟货币；没有稳定交易标识的旧客户端仍保留原兼容路径，后续可根据实际请求格式继续收紧。

随后补齐了抽卡兑换、箱式抽卡维护和带稳定标识的邮件领取事务边界：角色/装备兑换现在在 `gacha` 持久化命令中完成积分检查、奖励、收件历史和兑换点更新，箱式抽卡的关闭/重置也不再绕过协调器直接写主库；邮件领取在客户端提供 `request_id` 时可在网络重试后重放第一次结果。协议里的 `api_count` 只是可能重置的旧序号，不作为幂等键；只有请求带有稳定的 `request_id` 时才写入 `player_operation_receipts`，重试会返回第一次的完整响应并跳过再次发奖。旧客户端不带该字段时保持原有响应语义。该表和支付回执一样属于服务器幂等账本，存档导入时保留目标侧记录，不把它们作为可迁移的玩家进度。

默认路径仍是进程内队列，不等于所有 SQLite 已经搬到独立 worker。新增的可选 worker 只接收已经命令化的 SQL 写入；队列能避免实时回调直接同步等待写入，并提供同玩家串行和等待指标。要把主库完整交给 worker，仍必须先完成剩余写入口盘点、命令化和独立连接回滚验证。

主数据库事务仍在当前进程内执行，目的是先建立可替换的调用边界并获得基线数据，不启动新的主数据库写入者。幂等阶段新增支付回执和操作回执表，由初始化器创建；两表属于目标服务器账本，存档导入不覆盖。在线存档导入与默认模板统一接受 V2，旧 V1 模板不再应用，离线迁移工具的兼容函数继续保留。

隔离故障验证覆盖 checkpoint worker 的启动回写、长读事务导致的部分回写、维护写锁竞争与让位、分阶段空间回收、释放读事务后的继续推进、错误数据库路径恢复和停止清理；存档导入专项另覆盖 V2 对支付及操作幂等账本的保留，以及 V1 被拒绝且目标数据不变的回归。验证使用临时数据库，不代表云服运行实例已部署当前实现。

## 后续迁移顺序

1. 盘点并标记所有主数据库写入口：账号、玩家、单人关卡、抽卡、商城、邮件、任务、活动、排行榜、管理和维护。
2. 将领域事务逐组改为持久化命令，保持奖励、体力、任务和结算的原子性。
3. 为持久化命令加入请求幂等键、排队、失败恢复和关闭时 drain 语义。
4. 在隔离数据库上验证 worker 连接、事务回滚、忙等待、重复请求和存档导入导出。
5. 只有所有写入口都有统一所有者后，才把更多业务写入迁入独立持久化 worker；实时 TCP 与房间状态继续由单一 owner 管理。
6. 根据 CPU、事件循环、提交队列和内存实测结果决定是否拆 API 进程或迁移 MySQL。

MySQL 迁移的具体边界、SQL 方言清单、数据校验和回滚条件见 [MySQL 迁移方案](MYSQL-MIGRATION-PLAN.md)。

## 资源原则

四核机器不按“每个模块一个进程”分配。worker 数量、响应编码并发、NPC 操作和维护任务都必须有上限，并通过主进程与 worker CPU、内存、队列和事件循环指标进行调整。
