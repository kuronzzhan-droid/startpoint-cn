# 开发、分支与正式交付流程

本流程统一日常协作与正式交付，保护已有修改、运行数据和云服务器状态。

## 1. 分支与交付身份

| 对象 | 用途 |
| --- | --- |
| `main` | 唯一长期分支，承接日常开发、整合和验证 |
| `fix/`、`feat/`、`perf/`、`docs/` 临时分支 | 普通协作者的单任务分支，向 `main` 提交 PR，合并后删除 |
| `release-YYYY.MM.DD-N` 标签 | 固定正式交付的源提交，正式批次名与标签同名 |
| 源工作区 | Git 源码和本地 8001 测试服务的唯一来源 |
| 兼容运行镜像 | 非 Git 目录；状态路径回源，不作为源码或普通测试同步目标 |

不另保留长期集成分支，不需要晋级 PR 或合并后的分支回同步。`main` 上的最新代码不等于云服当前部署版本；标签固定源版本，交付记录分别记录包生成、标签发布、上传及部署状态。

`main` 保留 PR 和 hygiene 检查保护。普通协作者遵循 [协作与 PR 规范](../../CONTRIBUTING.md)：从最新 `main` 开临时分支，等待检查与评审后合并。仓库所有者在任务已获提交、推送授权且保护规则允许时，可以验证后直接推送 `main`。此例外不授权强推、删除 `main` 或关闭保护。

## 2. 操作授权

- “提交”“提交本地更新”“改好后提交”：只提交当前任务的明确文件，不推送。
- “推送”“推到 GitHub”“同步到远端”：推送当前任务已确认的改动；如尚未提交，先提交该任务明确文件。所有者日常目标为 `origin/main`；普通协作者推送自己的临时分支并开 PR。
- “提交并推送”“提交到 GitHub”：同时授权上述两步。
- 提交和推送只覆盖当前任务，不延续到后续修复或新发现的问题；不自动制作覆盖包、发布标签、上传包或部署。
- “分类提交”：按可独立审阅或回退的功能拆分 commit，包含该功能源码、编译输入、必要资源和配套文档；生成的 `out/` 不进入 Git。共享 manifest 随各类分包逐步更新，最终交付使用完整版本。
- “做整合包”“打包”：允许制作所指范围的云服覆盖包。默认只含上次正式交付后的本批变更；明确指定范围时按指定范围执行。旧待部署记录或偶然生成的 ZIP 不自动扩大范围或重置基线。
- “正式交付”“正式云服整合包”：本批包核验后创建并推送对应版本标签，属于该次正式交付范围；不因此推送尚未获授权的代码或部署云服。
- “只打包”：仅生成和验证本地产物，不创建或推送远端标签，不提交、推送代码。
- “发布标签”：需明确授权，使用打包工具的 `--publish-tag`；只发布本批具体标签。
- “部署到云服务器”：需单独明确授权；生成覆盖包或发布标签不等于上传、解压或重启线上服务。

## 3. 开始任务与提交

1. 记录当前分支、HEAD、上游、远端分歧、暂存文件、未暂存文件和未跟踪文件。所有者确认 `main` 跟踪 `origin/main`；协作者从最新 `main` 开单任务分支。
2. 检查远端引用及任务基线。保护已有修改；更新分支若会触碰脏文件，先解决范围，不自动 stash、reset 或 clean。
3. 只修改任务涉及文件，运行与风险相称的检查。TypeScript 运行代码变更需生成并核对本地运行产物，Git 只保存源码与编译输入。
4. 只暂存明确路径，禁止 `git add .`、`git add -A`、强推及改写已共享历史。实际暂存集合涉及源码、引用的数据、依赖、编译配置或运行产物策略时运行 `node tools/check-out-artifacts.cjs`；它隔离编译 Git index 的输入，不借用未暂存的源码或旧 `out/`。`--worktree` 仅用于开发检查，不能替代暂存集合。不要强制加入生成的 `out/`；仅文档等不影响编译输入时可跳过。详见[运行产物流程](runtime-artifacts.md)。
5. 检查暂存 diff，排除原有无关修改、密钥、`config/`、数据库、日志和临时产物。
6. 提交标题采用 `<type>(<scope>): <说明>`，默认中文说明；每条 commit 必须有正文，写明具体改动及原因或行为变化，内容以实际暂存 diff 为准。
7. commit 标题和正文不写测试、构建、验证命令或结果、CI 状态、基准、耗时和覆盖率等信息；这些写在 PR 或完成报告中。
8. 按本次授权提交、推送，并检查对应 SHA 的 hygiene 和 gitleaks 结果。失败时追加针对性修复，不改写已共享提交。

代码提交与标签是两种动作。正式标签指向已有代码提交，不为打包额外添加代码 commit。仅文档或交付工具改动无需制作新云服包或重启服务。

## 4. 本地试运行与空间控制

本地资源与客户端测试从源工作区启动，使用同一工作区的 `.env`、`.database/`、只读 `.cdn/` 及 `assets/asset-patch/active/` + manifest。

1. 确认 8001/8003 占用和目标工作区。已有目标服务就绪时复用；切换或重启前停止旧进程，不能让两个服务打开同一数据库。
2. 用 `scripts/start-cn-logged.ps1` 启动并写入 `.logs/`。仅在运行源码、依赖变化，`out/` 缺失或有效性存疑时重新构建。
3. 不复制整个源码树或生成默认源码副本；兼容镜像的状态路径回源。保留必要 CDN、客户端基线和资源，打包不自动清理它们。临时产物按需生成，清理仅针对另行明确的路径。
4. 本地 `.env`、测试开关、数据库、日志、依赖和备份不进入 Git 或云服包。
5. 确认服务就绪后交给客户端测试。普通增量检查编码、路径、ZIP 成员及回读、manifest 关系和受影响资源终态。

下载故障、版本不符、受影响 HTTP 路由或准入改动、明确 HTTP 验收时，按需使用 [CDN 手动检查工具](../../tools/cdn-http-probe.md)。客户端正在下载验收时不重复下载同批资源。跨版本起点使用真实客户端 `RES_VER` 或明确提供的资源版本，不把服务端上一条边当作设备状态。

## 5. 正式交付标签与文件集

标签格式为 `release-YYYY.MM.DD-N`：日期取正式交付时 `Asia/Singapore` 的真实日期，`N` 为当日从 1 开始递增的正整数。编号前检查本地、远端标签和交付记录，避免占用同一身份。标签固定本批已提交、已验证的源版本。

新正式交付使用新标签，不覆盖、删除或复用已发布标签。同批补漏、纠错沿用该批原始 `base`，生成完整替代包，不能把旧错误包的源提交当作新基线；已发布批次的替代成品分配新标签，仍保留原始增量基线。

文件集从原始基线到目标源提交确定，不从整个脏工作区复制：

- 服务端变更包含所需源码及固定目标提交完整编译后实际变化的 `out/` 产物；产物不要求在 Git 中存在。
- 游戏资源包含本批所需 JSON、manifest 和 active ZIP；本地运行文件集与云服文件集分别确定。
- 依赖变更包含 `package.json`、`package-lock.json`，部署说明列明安装要求。
- 删除路径单独显式记录，覆盖 ZIP 不会自动删除云端文件；执行删除前备份并取得相应授权。
- 文档、测试、开发指令和工具默认不进入云服包，除非云端运行必需或本身属于交付物。

目标路径有未提交编辑时，从源提交导出确定版本，不能将工作树混合内容封包。交付记录保留原始 `base`、源 SHA、标签、整包 SHA-256 及实际交付状态。

## 6. 生成云服覆盖包

仅在明确请求打包时执行。输出到工作区指定的交付目录，不默认放桌面。

```bash
python tools/build-cloud-overlay.py --release-tag release-YYYY.MM.DD-N --base <上一正式交付源提交> [--note <说明文件>]
```

`--release-tag` 可省略 `--batch`，默认批次与标签同名；正式交付若显式传 `--batch`，应与标签同名。包名为 `startpoint-cn-cloud-overlay-<release-tag>.zip`。旧 `--batch` 方式仍可用于兼容的非正式本地打包。

正式交付或另行明确发布该标签时加 `--publish-tag`；工具先完成包内容与 sidecar 校验，确认源提交已在远端 `main` 中且对应 hygiene 已通过，再创建并推送该具体标签，不推送其他标签或代码分支。只打包或本地试包不加此参数，不执行远端写入。

- ZIP 成员为安全的仓库相对路径，无额外外层目录、盘符、绝对路径或 `..` 跳转。
- 外层排除 `production/**` 和 `assets/asset-patch/production/**`，不包含 loose upload、medium_upload、android_upload、ios_upload。资源通过本批启用的 `assets/asset-patch/active/*.zip` 和 manifest 交付；内层 ZIP 的必要 `production/` 成员逐字节保留，不解包后再塞进外层。
- 不包含 `.cdn/`、`config/`、环境文件、数据库、日志、密钥、签名材料、备份、`node_modules` 或本地工作目录。
- 验证成员归属、安全路径及逐成员字节；静态文件与目标提交比对，生成物与该提交的隔离构建比对。整包只提供一份 SHA-256，不生成逐文件哈希。

配套提供 `<包名>.files.txt`（路径及字节数）、`<包名>.sha256.txt`、`<包名>.release.json`（版本身份和标签发布状态）及通过 `--note` 提供的 `<包名>.部署说明.txt`。涉及删除时，另提供 `<包名>.delete-files.txt` 并在文件清单中列出删除段。部署说明包含源提交、标签、适用云服基线、备份、覆盖位置、依赖或构建要求、重启、验证及回退方式。生成包、发布标签、上传和云服部署分别记录，不能把未部署内容标成云端实测。

## 7. 回退与完成报告

回退先确定当前云服实际版本，以它为 `--base`，用 `--source` 指定要恢复的已验证版本，制作专用回退包，无需切换工作区。`--source` 默认 `HEAD`，回退时必须显式指定：

```bash
python tools/build-cloud-overlay.py --batch <回退批次名> --base <当前云服源提交或标签> --source <目标恢复标签或提交> [--note <回退说明文件>]
```

明确恢复内容和删除路径，按清单备份后显式处理删除；ZIP 解压不会自动删除。不能把旧增量重新覆盖当作回滚；旧包可能不覆盖新文件，也不会撤销删除或数据库变化。数据迁移回退需按对应兼容性与备份方案执行。客户端已下载的 CDN 资源不能仅靠恢复旧 manifest 撤销，资源回退需另行制作兼容当前版本的增量链。需要把回退作为新正式交付时使用新的 `--release-tag`，并按正式标签规则发布，不改动旧标签。

完成时报告当前分支与提交、远端同步状态、实际运行的检查及 CI 结果、实际测试工作区、尚存无关修改和剩余步骤。只有实际制作了请求范围的包才提供产物链接、标签与 SHA-256，并分别说明标签是否发布、包是否上传和云服是否部署。
