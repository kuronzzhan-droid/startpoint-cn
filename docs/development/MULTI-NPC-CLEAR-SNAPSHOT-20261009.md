# 多人 AI 通关编队来源与冻结快照

## 行为

- AI 优先复用房间中已经确定且通过装备准入的 COM 编队；缺少或作废的 COM 席位从同分类、同关卡的通关历史中选择。
- 历史候选继续检查战力、特定关卡的属性及三个主角色；不足时可重复使用同一合格历史。
- 没有合格历史时使用通过装备准入的房主当前 TCP 编队。取消普通 NORMAL SET 扫描，不再把未通关 SET 当作 AI 候选；房主违规时等待修正，不复制违规队或使用固定模板兜底。
- 普通关卡的 AI 候选、COM 缓存与房主兜底含幻想专属武器或能力魂时整队拒绝；继续寻找下一支合格队伍，不卸装后继续使用。玩家 SET 不被此操作修改。
- 每个分类与关卡组合最多保留最近通关的 50 名玩家编队。取消最高战力保留名额，同一玩家再次通关覆盖原记录；同毫秒通关按玩家 ID 稳定排序。战力仍是选队门槛。

## 入池依据

此前成功结算按 partySlot 重读当前 SET。战斗中编辑同一 SET 后，结算可能错误地记录编辑后的编队。

现在与装备选择一起冻结真人连接的 TCP wireparty，仅在主角色、副位、武器、魂与选中 SET 一致且战力达到 8000 时采集。保存完整角色节点、EX、装备等级等 wire 数据；SET 只提供开战时的身份核对和战力。

HTTP 开战请求在房间队列内复制本玩家的快照、generation、参与者和救援标记，然后执行异步持久化。结算快照独立于 room，房主回大厅、新一轮开始或 room 删除都不会改写已经接受的开战请求。

成功结算只提交这一局的冻结快照；失败、abort、旧局无快照、SET 与 wire 不一致、固定队关卡均不录入。不会为缺少快照的旧局重读 SET。五重专用结算沿用现有路径。

## 数据与验证边界

- 沿用 `quest_ai_party_pool.db` 的既有表与 JSON 格式，没有存档 schema 迁移。录入、启动及重载按最近 50 策略整理现存记录。
- 现存历史按新容量策略继续使用，不清空历史池。旧策略已淘汰的近期记录无法恢复，旧 payload 也不能反证其实际出战来源；新逻辑只能保证此后采集来源。
- 针对性验证包含历史选择、快照深拷贝与身份检查、装备门禁、COM 续战、结算生命周期、worker 持久化与存档兼容。
- 本次为本地代码修改与隔离回归，未重启测试服、未完成客户端实战验收、未部署云服。

涉及运行产物为对应 TypeScript 的 `out/` JavaScript，包括 `quest-party-pool-shared.js` 和新增 `quest-party-snapshot.js`；后二者受 `out/` 忽略规则影响，后续提交时须显式加入精确路径。
