## 0. 这份文档为什么存在

**实证事故（非假设）**：

- `AGENTS.md` 在 2026-07-15 增加了「工程基线」章节；`CLAUDE.md` 停在 07-04，**未同步**。
- 结果：Claude 有一个月不知道三条硬约束——「新角色整包必须走 `wf_character_flow.py`」、
  「资产整理必须 scan→plan→preflight→quarantine→verify→restore drill」、启动器与端口纪律。
- 同期 Claude 在评审目录整理方案时，把一条**早已存在于 AGENTS.md 的既有规约**当作新建议提出。

**已修复**：两份文件现已合并为除首行标题外逐字相同，并由
`scripts/check-hygiene.sh` 的 `check_agent_docs_in_sync()` 把关。

> **【事实】Codex 静态复核（2026-08-11 06:04）指出初版门禁有洞**：仅在两份文件都存在时比较，
> **任一文件缺失直接放行**——删掉 `CLAUDE.md` 就能骗过 CI；且**没有任何 hygiene 回归测试
> 打得中这段逻辑**（既有 9 个用例的测试仓里两份文件都不存在，全部走"合法基线"分支）。
>
> **【已修复】Claude，2026-08-11**：判据改为**「git 是否跟踪」而非「盘上有没有」**——
> 只看盘上会留后门：删一份报错，**删两份反而放行**，绕过成本只是从 1 个文件抬到 2 个。
> 现行逻辑：既未被跟踪也不在盘上 = 合法基线；被跟踪却整体消失 = 失败；
> 只剩一份 = 失败；两份都在 = 比较内容。
> 补 6 个回归用例覆盖全部分支（`scripts/tests/test-hygiene.sh`，9 → 15）。
>
> ⚠️ 第二个后门是 Claude 在「要不要请 Codex 再复核」时自查发现的，**不在 Codex v1.9 的清单里**
> ——第一版修复只把绕过成本抬高了一档，没堵死。
>
> **变异验证**（本项目判据：删掉判定必须变红）：
> 还原成初版的「缺失即放行」→ `AGENTS.md missing…` 变红；
> 单独删掉「内容分裂」那句 `note` → `content divergence` 变红；
> 把判据退回「只看盘上有没有」→ `both tracked agent docs deleted…` 变红。**测试确实打得中。**

因此当前准确表述是：**两份都存在但内容分裂、或只存在其中一份，都会 CI 红。**

**结论**：两个执行者共用同一份规则书是硬要求，不是建议。

## 1. 角色分工

**【决定】两者同级同位（作者 2026-08-11）**：Claude 与 Codex 是**平级工具**，
目标同为辅助开发本项目的工具链。**两者都写生产代码，都做设计，都做验收。**

> **本条取代 2026-08-02 的旧分工**（「Claude 只做设计与判断，所有 coding 交 Codex」）。
> 旧分工的理由是 token 限额，属于成本调度考量，不是能力或职责边界。
> **成本仍可作为派活时的参考，但不再是谁能做什么的规则。**

### 1.1 分工按「任务」切，不按「工种」切

| 旧模型（已废弃） | 新模型 |
|---|---|
| Claude 设计 → 交接 → Codex 施工 | **谁接的活谁做完**（设计、实现、测试、验收一条龙） |
| 每个任务都有一次交接 | 无交接 |
| 风险：交接处事实过期、错误被放大 | 风险：**两个执行者可能同时改同一批文件** |

**交接消失了，但文件争用出现了。** 处理见 1.2。

### 1.2 并发互斥：文件占用与 worktree 隔离

**同一时刻只有一个执行者能在主工作区 `D:\WF\startpoint-cn` 直接改同一批文件。**

- **占用判定（客观，v1.13）**：开工前按顺序查 ① 对方实时状态文件顶部「占用文件/owner」段；
  ② `git worktree list` 及各 worktree 的未提交改动；③ `mod-tools/work/sync_pending.json`（口径见 7.1）。
  三处都没有该文件 = 未占用，直接做，并把占用登记进 `work/agent-coordination/当前状态.md` 与自己的实时状态。
- **主工作区默认由当前会话独占**：判定无人占用即可在主工作区直接改、构建、提交；只有查到登记冲突
  （对方登记了同一文件或有在途 worktree）才将可隔离的源码工作放入 worktree（Codex 惯例 `.worktrees/<任务名>`）。
  在 worktree 里完成的改动，任务结束前本地合回当前工作分支（merge / cherry-pick），这是任务的一部分；push 仍需作者要求。
- 数据表、文档、配置这类作者随时在动的东西，两边都**先查 `sync_pending.json`**（口径见 7.1），并且**不许整表覆盖**
- 查到占用冲突后，先隔离源码工作；不重叠的调查、实现和验证继续。worktree **不隔离共享 live store、共享表或 pending**，
  冲突数据写入必须暂停；无法安全隔离或合回时，报告具体冲突并问作者，不自行覆盖。没有登记冲突时先完成上述核查，不因「拿不准」停工。

**Codex 子代理隔离规则**：会话提供的并发槽、工具和上下文继承方式会变化，具体值只写入
`work/agent-coordination/codex-to-claude.md`，不固化在本协议。除非当前运行时明确提供了独立 worktree，
否则必须假定 root / child 共享 cwd 与文件系统，**创建子代理本身不等于创建隔离**。

- 独立只读调查或明确不重叠的文件可并行；任何共享文件写入必须串行，并先在实时状态里登记 owner；
- 派发前把当前并发上限、可用工具、上下文继承方式和禁止项写进 brief / 实时状态；
- 完成、中断或阻塞后必须把终态写进状态文件；侧栏累计时长不能代替运行状态证据。

### 1.3 相对强项（派活参考，不是职责边界）

这一节**不构成限制**，只是作者派活时可参考：

| | 相对更适合 |
|---|---|
| Claude | 需要跨源交叉验证、推翻既有结论、逆向语义、判断"这条路走不走得通" |
| Codex | 大批量机械改造、长时间连续施工、按已定规格铺开 |

**任一方接到不属于自己"强项"的任务，照做，不推诿。**
判断力不够时的正确动作是**查证**，不是转手。

### 1.4 接管（failover）—— 同级的真正理由

**【决定】作者 2026-08-11**：两者都可能限额吃紧，**一方限额，另一方顶上**。
这是"同级同位"的操作性理由，不只是名义上的平级。

#### 这条推翻了本文档早期的一个判断

早期版本写着「风格差异不是冲突，不处理，角色不同风格本就该不同」。
**在接管前提下那是错的**——接手一份半成品时，对方的记录方式、提交粒度、
验收标准如果和自己不同，接管成本会陡增，甚至会把已完成的部分推倒重做。
**故：开发风格必须对齐。**

#### 核心约束：限额耗尽是无预警的

**不能依赖"交接时写一份交接文档"**——真限额了就没机会写。因此：

| 要求 | 说明 |
|---|---|
| **边做边更新，不是做完再写** | 每完成一个可描述的步骤就更新状态，任何时刻中断都能被接管 |
| **小粒度提交**（作者纪律第 3 条） | 已提交的单元是确定状态。**这条规则本身就是最好的接管保障** |
| **未提交的东西必须被记录** | 否则接手方无从判断工作区里那些改动是什么、能不能动 |

#### 载体：复用既有的 `work/agent-coordination/`

仓内已有 `claude-to-codex.md` + `codex-to-claude.md`（含任务板、文件所有权、
「勿重复接」并发标记），**最后更新停在 2026-07-18**。恢复使用，但协议改为**对称**：

- 旧协议：Claude 维护任务板，Codex 执行后回报（对应已废弃的按工种分工）
- **新协议：各自维护自己那份，内容是「我现在的实时状态」，另一方随时可读可接管**

每份至少包含：

```
- 当前任务与目标
- 工作区位置（worktree 路径 / 主工作区）
- 已完成到哪一步（对应哪些 commit）
- 工作区里未提交的东西是什么、能不能动
- 下一步准备做什么
- 我正在占用哪些文件（文件所有权，防对方并发改）
- 已知阻塞 / 待作者拍板项
- 接管所需时，补充**当前会话实际**的 Skill / plugin / tool / 权限轮廓（只记名称、版本、
  启停和作用域，绝不记录 secret 或环境值）
```

**入口与体量（v1.13）**：`work/agent-coordination/当前状态.md` 是不带日期、始终当前、不超过 60 行的共同入口
（链尾、服务口径、进行中任务与占用文件、待拍板、指向最新详细记录），两个执行者每完成一个单元都更新它。
各自的实时状态文件只保留「当前状态」段 + 最近 3 条记录，更早内容移到 `*.archive-<日期>.md`。

#### 接管方的动作

1. **先读对方那份状态文件**，不要凭工作区现场猜
2. 未提交改动**先判断归属再动**——可能是对方做到一半的，也可能是作者的 WIP
3. 沿用对方已建立的结构，**不重构已完成部分**
4. 状态文件与现场不符 → 按第 3 节判定影响范围；需作者处理的分歧集中报告，独立已授权工作继续

#### 「开发风格对齐」具体指哪些项

本文档已覆盖大部分，此处归拢便于核对：

| 项 | 对齐要求 | 定义在 |
|---|---|---|
| 实时状态记录 | 边做边更新，含未提交物与文件占用 | 1.4 |
| 并发互斥 | worktree 隔离 + 文件所有权 | 1.2、1.4 |
| 提交粒度 | 单个模块/功能完成即提交；禁 `git add -A` | 7.0 第 3 条 |
| 事实标注 | 【事实】/【判断】/【决定】三层，双向 | 2 |
| 遇到分歧 | 暂停受影响操作并报告，独立已授权工作继续，不自行覆盖 | 3、4 |
| 文档去向 | 设计入库 specs/，计划落 `work/plans/` | 6 |
| 测试标准 | 改行为走 TDD，改数值内容走真机 | 6（边界表） |
| 验收标准 | 静态检查不等于验收；新表/新路由要起服探针 | 7.3 |
| 判断纪律 | 否定结论必须给搜索面；基线必须点名 | 7.2 |
| 语言 | 需审查的文档用中文 | 7.0 第 5 条 |

**不要求对齐的**：分支命名前缀（`claude/*` vs `codex/*` 保留，便于溯源）、
内部推理方式、单次回复的详略。这些不影响接管。

## 2. 事实 / 判断 / 决定 —— 三层标注（强制）

任一执行者写给另一方（或写给作者）的任务书、规格、评审、交接，
**必须逐条标注属于哪一层**。两者同级，**这条对双方对称生效**。

| 标注 | 含义 | 必须附带 | 对方可否质疑 |
|---|---|---|---|
| `【事实】` | 实测得到的客观状态 | **来源 + 时间戳** | ✅ 实测不符时**必须**质疑 |
| `【判断】` | 推理得出的结论 | **置信度**（高/中/低）+ 依据 | ✅ 有反证即质疑 |
| `【决定】` | 已拍板的取舍 | 拍板人（作者 / Claude / Codex） | ❌ 不得自行改；有异议先报告 |

**示例**：

```
【事实】merge-base == 76223aa6（`git merge-base` 实测，2026-08-10 23:40）
【判断】M 桶 180 个文件可能基于我方旧状态（置信度：中；依据=对方 CI 已知三处预期红）
【决定】共享表一律键级三向并集，禁止整文件覆盖（拍板：作者；理由=整表读改写回曾致后写者全覆盖）
```

**未标注的任务书，接手方应退回要求补标注**（双向），不要凭猜测区分。

> **⚠ 知识不对称（Codex 必读）**：Claude 有一份持久记忆库（105 条，位于用户 profile 下），
> **Codex 看不到**。其中多数硬事实在 `mod-tools/docs/` 有对应文档，但**不是全部**。
>
> 因此：**Claude 写的【事实】必须给出仓内可查的出处**（文件路径 / 命令 / 提交哈希）。
> 若只写结论不给出处，**Codex 应直接要求补出处，不要默认它有据可查**。
> 反向同理——Codex 若有只存在于其侧配置或会话历史的依据，也须落到仓内可查处。
>
> **Codex 侧也可能有独立持久记忆**，Claude 不可假定能读取；
> 记忆内容可能过期，也不是本文档的替代权威。Codex 若使用记忆中的事实，必须标明来源并重新
> 核对易漂移项；需要跨执行者接管的结论仍须落到仓内文件、命令或 commit 证据。

## 3. 发现不符：核查事实，暂停受影响操作（强制）

**每份任务书必须包含以下原文**：

> 若实测与本文【事实】不符，先补证据并判定影响范围。可漂移的状态更新记录后继续；
> 影响方案前提、授权范围或作者【决定】时，暂停依赖该前提的操作，报告差异并问作者，不自行改定方案。
> 【判断】被反证或双方仍有实质结论分歧时同样处理。继续完成不依赖该分歧的已授权工作，不以局部分歧冻结整轮任务。

**理由**：任务书里的【事实】会过期，写的人也会判错（Claude 侧有确凿记录，见 7.2；
Codex 侧同理适用）。而接手方倾向于忠实执行给定前提，不会主动怀疑。
这条是最便宜的止损——**一个人的错误不会被另一个人放大成一整轮施工**。

**双向生效**：谁写任务书谁附这段，谁接任务书谁执行这段。

**不符的分级（v1.13）**：会漂移的值（PID、链尾/版本号、行数、时间戳、目录下文件数）与任务书不符时，
记录差异后继续；影响方案前提的不符（表结构、列位、机制判断、授权范围、【决定】）按上面的模板暂停受影响操作并报告。

## 4. 冲突处理协议

| 冲突类型 | 处理 |
|---|---|
| **事实冲突**（双方对同一客观状态说法不同） | **实测为准**。谁的说法与实测不符，谁改。附上复现命令 |
| **判断冲突**（同一事实，结论不同） | **双方暂停依赖该判断的操作，报告并问作者**；独立已授权工作继续，不许任何一方自行覆盖 |
| **决定冲突**（触及已拍板项） | **暂停触及该决定的操作并问作者**。拍板项只能由作者改，其他已授权工作继续 |
| **风格差异**（记录方式、提交粒度、验收标准不同） | **按现行共同规则对齐**；仍影响交付且无法对齐时报告具体差异。只暂停受影响部分，不扩大为整轮停工 |

**默认值**：分不清是事实冲突还是判断冲突 → 先补实测；实测能分辨的按事实冲突处理（谁错谁改）。
实测之后仍是实质结论分歧，才暂停受影响操作并问作者；未受影响的工作继续。

**保留的 `test-driven-development` 有适用边界（重要，否则会冲突）**：

| 改动对象 | TDD 适用？ | 验收方式 |
|---|---|---|
| `src/`、`admin/`、`mod-tools/` 的**代码**（含发布器、校验器、接收器的行为） | ✅ 适用 | 对应单元/契约/集成测试；测试数量会漂移，不在协议中硬编码 |
| `assets/*.json` 等**游戏数据表** | ❌ **不适用** | **真机跑一把**。给"某角色伤害倍率 +10%"写单元测试没有意义 |
| 一次具体的发布、CDN/store 内容写入或产物安装 | ❌ 不用 TDD 模拟授权 | 发布前完整性门禁 + 写后回读；需要时再做服务/真机确认。**这不豁免发布工具代码的 TDD** |

**判据**：改的是**行为**（代码怎么算）→ TDD；改的是**数值或内容**（算什么）→ 真机。
真机验收要求保留。尚未实测时，可先交付已完成的静态检查、本地发布及回读，明确标注「游戏未验收」；
不得把这些证据替代真机结果，也不得把任务仍要求的游戏验收标成完成。
另注意 superpowers 的 TDD 原文要求「测试之前写的代码一律删掉重来」，
**该要求只对生产代码成立**，不得套用到数据改动或一次性调查脚本上。

> **修复本失效模式的动作本身又制造了一次同样的失效。**
>
> **根因**：本文档是**活文档**，会持续修订。**复制活文档 = 制造 N 个必然过期的副本。**
>
> **旧分支工作副本已改为指针**：17 份原有副本已替换为指向权威路径
> `D:/WF/startpoint-cn/docs/协作对齐-Claude-Codex.md` 的存根，不再承载内容。
> **今后不得手工复制活文档形成无人维护的全文副本。**
>
> **【事实】当前指针仍是本机工作副本机制，不是 branch 持久机制**（Codex 复核，
> 2026-08-11 06:04）：17 个存根均为相同的 774-byte 未跟踪文件，`git status` 会显示 `??`；
> 0 个对应 branch tip 含存根，也没有自动创建/检查脚本。worktree 被重建或存根被清除后指针会消失。
> 这些 `??` 不得随业务 commit 带入，也不得据此声称新 worktree 自动拥有指针。
>
> **Git 语义限定**：若目标 branch 不跟踪本文档，可创建同样的未跟踪指针；若目标 branch 已跟踪
> 本文档，Git 会检出该 branch 的全文快照，此时**不得把 tracked 文件覆盖成指针**（会制造 `M`）。
> 两种情况下开工都必须读取主工作区权威路径并核对版本；权威路径打不开就停下来问作者。
>
> `CLAUDE.md`/`AGENTS.md` 是另一种情况——当前主分支两份均受 git 跟踪；旧 branch 可能只跟踪
> 旧版，或缺其中一份。只有 branch 实际接收相应 commit 后，tracked 副本才会随 merge/rebase 更新；
> 当前工作副本中的 `M` / `??` 不具备这种持久性。
> 但**若在主工作区再次修订规则书，各 worktree 仍需重新同步**（门禁抓不到，见下）。
> 当前 17 个工作副本虽已与主规则一致，但都是本地修改；对应 branch tip 中 14 个仍是旧规则，
> 另 3 个缺 `AGENTS.md`。这说明“当前磁盘已同步”不等于“分支已持久同步”。

**门禁的设计限制仍然存在**：`check_agent_docs_in_sync()` 只比较同一棵树内的两份文件，
无法发现「整棵树都是旧版」。**新开 worktree 或长期未同步的 worktree，
进去干活前应先确认规则书版本**：

```bash
diff <(tail -n +2 AGENTS.md) <(tail -n +2 /path/to/worktree/AGENTS.md)
```
